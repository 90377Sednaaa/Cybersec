01 · The short version

The one-minute version

Aletheia is a health check for a web application you are authorized to test. It looks around, inspects what is exposed, interprets what it found, and then asks a human to decide what is real.

Four things happen in order, and each one answers a different question:

  1. Discover. DNS and Nmap answer: where is this application, and which network doors are open?
  2. Inspect. The prober and OWASP ZAP answer: what does the application expose, and how is it configured?
  3. Interpret. A rule engine and an AI model answer: which observations are worth calling findings, and what might they mean together?
  4. Decide. A human assessor answers: is this real, how bad is it here, and what should be done?

The single most important design rule is the last one: nothing is a confirmed vulnerability until an assessor verifies it. Tools are good at seeing facts and bad at understanding context. People are the reverse. Aletheia is built so that neither side is allowed to do the other's job.

Why it is shaped this way

Cheap, deterministic checks run first. Expensive and intrusive checks run later, and only when the target's authorization allows them. If one tool is missing or crashes, that job fails and the rest of the run continues. A missing Nmap install should never destroy an assessment that already has useful header findings.

02 · Vocabulary

The mental model

Seven words carry most of the system. Once these are clear, the rest of the document is detail.

Table 1. The core objects
TermWhat it means in Aletheia
Target A registered web application: a name, a base URL, an authorization reference, a scope list, and an allowed scan intensity.
Assessment One run against one target. It has an intensity, a set of categories, a status, and a timeline of jobs.
Job One tool doing one piece of work. Jobs have their own status, progress, log, and raw output. They succeed or fail independently.
Raw output The structured result a tool produced, stored as JSON on the job. It is evidence, not a finding.
Finding A specific weakness or observation worth a human's attention: title, description, category, severity, status, remediation.
Evidence The proof attached to a finding: a tool output snippet, an HTTP request/response transcript, or a file uploaded during verification.
Assessor The logged-in human with permission to verify, dismiss, or request more evidence. Their identity and timestamp are recorded.
The analogy that fits best

Think of a building inspection. The target is the building and its address. Authorization is the owner's written permission to enter. Intensity is how far the inspector may go: look through the windows, or open the service panels. Each tool is a specialist: the electrician, the plumber, the structural engineer. Their notes are observations. The surveyor reads the notes, checks the ones that matter, and signs the report. Aletheia is the building, the specialists, and the surveyor's desk, in one system.

Every finding answers three questions

This is the cleanest way to understand the data model. A finding is not just a sentence; it carries three independent pieces of information:

  • What is it? The category (for example, "Security configuration & HTTPS") and the description.
  • How bad is it? The severity tier and, when the assessor sets one, a 0–10 score.
  • How sure are we? The status (ai_candidate, verified, needs_evidence, false_positive) and, for AI-produced findings, an ai_confidence value.

Keeping these separate matters. A finding can be severe but uncertain, or certain but minor. Collapsing them into one number is how dashboards end up lying.

03 · Orchestration

The pipeline, step by step

A run is a fixed sequence of steps, executed in-process, with live progress streamed to the browser. The order goes from least intrusive to most intrusive on purpose.

Table 2. Execution order
#StepQuestion it answersWhat it produces
1DNSWhere does this name point?IPv4/IPv6 addresses, mail/name/text records, optional subdomain hits.
2NmapWhich network ports are open, and what is listening?Hosts, open ports, service names, product and version guesses.
3ProberWhat does the web response reveal about configuration?Headers, cookies, TLS facts, exposed paths, deterministic candidate findings.
4ZAP full onlyWhat can an automated attacker find in the application?Spider map plus alerts with risk, confidence, evidence and CWE.
5NormalizerWhich tool statements are unambiguous enough to become findings?Candidate findings from the prober and ZAP, deduplicated by title.
6AI interpreterWhat do the raw outputs mean together?Up to 10 additional candidates, schema-constrained, confidence-scored.
7AssessorWhat is actually true and how bad is it here?Verified, dismissed, or evidence-requested findings, with an audit trail.

Why ZAP is last

ZAP's active scan is the only part of the pipeline that deliberately sends attack payloads. Running it last means the passive results already exist before anything intrusive happens, and a cancelled or unauthorized run can stop before that point without losing the rest. The escalation is deliberate: observe first, poke second, attack only with permission.

The intensity gate

Every target has an allowed_intensity: passive_safe or full_intrusive. A run also has a requested intensity. The lower of the two wins, and the check happens twice.

The second check exists because of a real gap: an assessment freezes its intensity when it is created, but a target's allowed level can be lowered afterwards. Without the re-check, a run created yesterday could use yesterday's permission today. The orchestrator therefore computes an effective intensity and uses that everywhere, including inside each tool.

Jobs, logs, and graceful failure

Each job writes a log, a progress value between 0 and 1, and its final status. The browser subscribes to a server-sent event stream, so progress appears without polling. The stream is best-effort by design: if a client falls behind, old events are dropped rather than growing memory without bound, and a fresh snapshot recovers the current state.

A tool that cannot run raises an error with an actionable message. The orchestrator marks that job failed, logs it, and moves on. Typical examples: Nmap is not on PATH; the ZAP daemon is not listening; the target refuses connections. The assessment still completes with whatever the other tools produced, and the notes explain what was skipped.

In the code

backend/app/scanner/orchestrator.py owns the order and the gate. BASE_TOOLS = ["dns", "nmap", "prober"]; INTRUSIVE_TOOLS = ["zap"]; effective_intensity() performs the re-check; _run_job() isolates failures.

04 · Reconnaissance

DNS: finding the address before knocking

DNS is the internet's phone book. Before a tool can talk to shop.example.com, something has to turn that name into an IP address. That is the whole job of this step, plus a little context.

What it collects

Table 3. DNS record types used
RecordPlain meaningWhy an assessor cares
A / AAAAThe address of the server: IPv4 and IPv6.Confirms where the application actually lives, including localhost during a lab run.
MXWhich servers receive email for the domain.Hints at mail infrastructure and third-party providers in scope.
NSWhich name servers are authoritative for the domain.Reveals the DNS host and can suggest shared or outsourced infrastructure.
TXTFree-text records, often used for verification and email policy.Can disclose vendors, SPF/DMARC posture, and ownership hints.

Address lookup uses the operating system resolver (getaddrinfo) rather than a hard-coded DNS server. That is deliberate: it respects the local hosts file, which is how a Juice Shop instance running at localhost is reachable in a lab. MX, NS and TXT lookups use dnspython when the target is a real domain.

Subdomain probing

At full intensity, the runner tries ten common names in front of the target host: www, mail, api, dev, staging, test, admin, portal, vpn, intranet. Any name that resolves is recorded with its addresses. This is not a brute-force engine; it is a small, fast check for forgotten environments.

Why this is still behind the gate

DNS lookups are non-destructive, but they are still outbound traffic to third-party name servers. Keeping them behind the intensity gate keeps a passive assessment genuinely minimal, and keeps the rule simple: no authorization, no extra probing.

Every lookup has a five-second cap. A stalled resolver cannot pin a worker thread forever, and the job records "resolver timed out" rather than hanging the run. DNS output does not create findings by itself; it is context for the AI interpreter and evidence for the assessor.

05 · Port scanning

Nmap: which doors are open

A server is a building with 65,535 numbered doors per protocol. Most are locked or bricked up. Nmap knocks on a selected set, notes which ones answer, and asks the ones that do: "who are you?"

Ports, in plain language

An IP address identifies a machine. A port identifies a conversation on that machine. Web traffic normally uses port 80 (HTTP) or 443 (HTTPS); a development server often uses 3000 or 8000. A service that is listening on a port is reachable by anything that can route to that address. That is why open ports matter: every one is a potential front door, and some are not supposed to be public.

The two profiles

Table 4. Nmap arguments per intensity
IntensityArgumentsWhat that means
passive_safe --top-ports 1000 -sV Scan the 1,000 most common ports and identify the service on each open one.
full_intrusive --top-ports 5000 -T4 -sV Scan 5,000 ports, use a faster timing template, and still identify services.

"Top ports" is not a random sample. Nmap ships a frequency-ordered list derived from large internet scans, so the first 1,000 ports cover the overwhelming majority of real services. Scanning all 65,535 ports would be slower, noisier, and mostly empty.

-sV is service version detection. Nmap sends a few small probes and reads the reply: a banner, an error page, a protocol handshake. From that it guesses the product and version, for example "Apache httpd 2.4.58". The guess is useful context, not proof.

What is deliberately not run

  • No OS detection (-O). It needs raw sockets and administrative privileges, which on Windows means Npcap. The project runs natively without that requirement.
  • No NSE scripts. Nmap's scripting engine can be intrusive, and some scripts exploit rather than observe. They are outside the platform's authorization model.
  • No ping sweep or broad subnet scan. Aletheia scans the registered host, not the network around it.

How the target is extracted

Nmap wants a host and a port, never a URL. The runner parses the registered base URL, takes the hostname, and adds -p <port> only when the URL specifies one. It also rejects a hostname beginning with a hyphen, because Nmap would read that as a command-line flag and escape the conservative profile.

A detail worth knowing

If the registered URL includes an explicit port, for example http://localhost:3000, Nmap scans only that port. It does not also sweep the top 1,000. For a lab target that is exactly what you want. For a production host registered as https://example.com with no port, it scans the top 1,000. This behaviour comes from -p taking precedence, not from a bug, but it changes what "Nmap found nothing" means.

From XML to structured output

Nmap writes XML to standard output (-oX -). The parser keeps only what the platform needs: each host's address and hostname, and each port whose state is exactly open, with its protocol, service name, product, and version. Closed and filtered ports are discarded. The summary line ("Nmap done: 1 IP address scanned in 12.4 seconds") is kept as a human-readable note.

Two operational safeguards matter. A hard 15-minute cap kills a hung scan instead of hanging the assessment forever. And if the nmap executable is missing, the job fails with a message that says how to install it, while the pipeline continues.

In the code

backend/app/scanner/nmap_runner.py: PROFILES holds the arguments, build_nmap_target_args() extracts host and port, parse_nmap_xml() is a pure function tested against a fixture without Nmap installed.

Nmap does not create findings in the rule-based normalizer. An open port is a fact, not automatically a vulnerability. Its output becomes context for the AI interpreter and evidence for the assessor, who decides whether an exposed service is expected.

06 · HTTP inspection

The prober: reading the front door's paperwork

The prober is Aletheia's own engine, with no external tool behind it. It sends one ordinary web request, then reads the response the way an inspector reads the labels on a shipment: status, headers, cookies, certificate.

What an HTTP conversation looks like

Every web page is a short conversation. The client sends a request line and some headers; the server sends a status code, its own headers, and a body. The prober does not need to understand the body to learn a lot from the envelope. 

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Server: nginx/1.24.0
Set-Cookie: session=abc123; Path=/

<!doctype html> ...

A response like the one above already tells an assessor three things: the server software and version are public, the session cookie has no HttpOnly or Secure flag, and none of the six security headers are present. None of that required an attack. It is all in the paperwork.

The header checklist

Table 5. Security headers the prober checks
HeaderWhat it does, in plain languageIf missingWhy that severity
Content-Security-Policy Tells the browser which scripts and sources are allowed to run. It is a seatbelt against injected scripts. high It removes a major defence against cross-site scripting. The app may still be safe, but it has lost its safety net.
Strict-Transport-Security Tells the browser to use HTTPS for this site from now on, even if a link says http. medium Without it, a network attacker can try to downgrade a visitor to plain HTTP.
X-Content-Type-Options Stops the browser from guessing a file's type and treating, say, an image as a script. low The expected value is nosniff; absence is a hygiene gap that makes some upload attacks easier.
X-Frame-Options Stops another site from loading this page invisibly inside a frame and tricking clicks. low Clickjacking needs a plausible lure; the missing header is a weakness, not an exploit by itself.
Referrer-Policy Controls how much of the current URL is shared with the next site. low URLs sometimes contain tokens or internal paths; the leak is real but usually small.
Permissions-Policy Restricts access to camera, microphone, geolocation and similar browser features. info Useful hardening, but rarely the difference between safe and unsafe.
The key distinction

A missing header is not the same as a working exploit. It is a missing defence. That is why the prober caps most of these at high rather than critical, and why every one of them is still only a candidate until an assessor confirms it. A static marketing page missing a CSP is a much smaller problem than a banking page missing one.

Cookies

A cookie is a note the server asks the browser to keep and send back on every request. Session cookies are effectively temporary passwords. Two flags decide how safely they are handled:

  • HttpOnly means JavaScript cannot read the cookie. Without it, any script injection can steal the session.
  • Secure means the cookie is only sent over HTTPS. Without it, a single plain-HTTP request can expose it.

Each missing flag becomes a low-severity candidate in the "Session management" category, with the cookie name in the title so the assessor can find it.

Information disclosure

Two response headers advertise the stack: Server and X-Powered-By. Their presence produces an info finding. This is not a vulnerability. It is free reconnaissance for an attacker: why spend time guessing the framework version when the server tells you? Removing the header does not fix anything by itself, but it raises the cost of targeted attacks.

TLS certificates

For HTTPS targets the prober opens a separate TLS connection and reads the certificate directly. It deliberately does not verify the certificate chain, because a self-signed certificate is exactly the kind of thing the assessment should be able to report. Three conditions produce findings:

Table 6. Certificate checks
ConditionSeverityWhy
ExpiredhighBrowsers refuse the connection or show a full-page warning. The site is effectively broken for careful users.
Expires in under 30 daysmediumAvoidable outage; the fix is a renewal, and the clock is visible.
Self-signedmediumNo trusted third party vouches for the certificate, so users cannot distinguish the real site from an impersonation.

A certificate is a passport: it binds a name to a key and is signed by someone others trust. An expired passport is not forged, it is simply no longer accepted. A self-signed one is a passport you printed yourself: valid inside your own house, meaningless at the border.

Exposed paths, at full intensity only

The prober requests a short, fixed list of paths that should never be public. A response with a status below 400 counts as reachable. It does not download or exfiltrate anything beyond the response itself.

Table 7. The probe list
PathSeverityWhat exposure would mean
/.envhighEnvironment files commonly hold database passwords and API keys.
/.git/HEADhighAn exposed repository leaks the full source history, including old secrets.
/backup.zip, /backup.tar.gzhighArchives often contain source code, database dumps, and configuration.
/debug.log, /error.logmediumLogs leak stack traces, internal paths, and sometimes credentials.
/admin/mediumAn admin surface reachable without a gate at that path.
/server-statusmediumApache's status page discloses live requests and internal endpoints.
/composer.json, /package.jsonlowDependency manifests reveal exact versions, which makes known-vulnerability matching trivial.
/.DS_StorelowmacOS metadata leaks directory names and file listings.

Before any probe, the list is filtered against the target's out-of-scope assets. An entry such as /admin in the out-of-scope list removes every path under it, and the job log says how many were skipped. The filter is prefix-based and runs on the normalized path, so a full URL and a bare path behave the same.

Deterministic does not mean confirmed

Every prober result is a rule outcome: a header is present or absent, a flag is set or not, a certificate date is past or future. There is no guessing, which is why these candidates are created with a confidence of 1.0. But they are still inserted as ai_candidate. The rule can be certain about the fact and still wrong about the conclusion: a missing header may be a deliberate, compensated decision.

Honest edge cases

The prober follows redirects. A request to /admin/ that redirects to a login page and ends at HTTP 200 is still counted as "reachable", even though the panel is gated. That is a false positive waiting to happen, and it is exactly why the assessor opens the evidence and decides. TLS facts are only collected for HTTPS on port 443, and the Secure cookie flag is checked even on a plain-HTTP target, where it cannot be set meaningfully.

In the code

backend/app/scanner/prober/__init__.py performs the requests; prober/checks.py holds SECURITY_HEADERS, PROBE_PATHS, check_tls(), and the scope filter. All checks are pure functions, tested against canned responses.

07 · Application scanning

ZAP: the automated attacker, when allowed

OWASP ZAP is a full web application scanner. Aletheia drives it through its REST API in daemon mode. ZAP does two very different things, and the difference is the whole reason the intensity gate exists.

Table 8. Spider versus active scan
ModeWhat ZAP doesRisk to the targetWhen Aletheia runs it
Spider Clicks through the site like a curious user: follows links, submits forms, builds a map of pages and parameters. Low. It is ordinary browsing, though it can create sessions or submissions. Always, at both intensities.
Active scan Sends attack payloads at every input the spider found: injection strings, script tags, path traversal, malformed requests. Real. It can modify data, trigger errors, fill logs, and occasionally break a fragile page. Only at full_intrusive, and only if the target allows it.

That is the honest answer to "why can't it just scan everything?" Because an active scan is an attack. It is an authorized, bounded attack, but it is still traffic designed to make the application misbehave. A target marked passive_safe gets the spider and nothing more.

How Aletheia drives it

  1. Connect to the ZAP daemon and read its version. If it is unreachable, the job fails with the exact command needed to start it.
  2. Start the spider on the target's base URL and poll its status every two seconds.
  3. At full intensity, enable all passive scanners, start the active scan, and poll again.
  4. Fetch up to 500 alerts for the base URL and normalize them into Aletheia's structure.

Each phase has a ten-minute cap, implemented as 300 polls at two-second intervals. Cancellation is checked between polls. A missing daemon degrades gracefully: that job fails, the rest of the assessment continues, and the notes say why.

Anatomy of a ZAP alert

Table 9. What Aletheia keeps from an alert
FieldMeaning
nameThe alert title, for example "Content Security Policy (CSP) Header Not Set".
riskZAP's own severity: informational, low, medium, or high.
confidenceHow sure ZAP is that the alert is real, not how bad it is.
urlThe exact page where the evidence was observed.
evidenceThe snippet that triggered the alert, capped at 500 characters.
description / solutionZAP's explanation and remediation advice, capped at 1,500 characters each.
cweidThe Common Weakness Enumeration identifier, when ZAP provides one.
Risk is not confidence

These two numbers are constantly confused. Risk answers "how bad if true?". Confidence answers "how sure is the scanner that it is true?". A high-risk, low-confidence alert deserves investigation, not panic. Aletheia keeps both, and the assessor weighs both.

Mapping ZAP into Aletheia's categories

ZAP does not use Aletheia's five categories, so the normalizer maps alert titles by keyword. Anything unmatched defaults to "Input validation & injection", because that is what most active-scan plugins probe for.

Table 10. Keyword mapping
If the title containsCategory
cookie, session, csrfSession management
header, hsts, csp, https, tls, certificateSecurity configuration & HTTPS
directory browsing, backup, cross-domain, sensitive file, .env, gitExposed files & directories
disclosure, information leak, banner, debug, traceInformation disclosure
anything elseInput validation & injection

Risk mapping

ZAP's four-level scale maps one-to-one onto Aletheia's lower four tiers: informational → info, low → low, medium → medium, high → high. ZAP has no "critical" level. As a result, a critical finding in Aletheia always comes from an assessor's judgement or an AI suggestion that an assessor accepts, never directly from ZAP.

The one limitation that matters most

ZAP follows links and attacks whatever it can reach from the seed URL. Aletheia checks the authorization of the registered target before handing it over, but it cannot police every hop ZAP takes afterwards. This is documented in the runner. The practical rule is simple: only point ZAP at a host whose owner has authorized testing of that host and everything it links to.

ZAP also only sees what it can reach. Pages behind a login, multi-step flows, and JavaScript-heavy single-page apps may be under-mapped. A clean ZAP result is evidence of coverage, not proof of safety.

In the code

backend/app/scanner/zap_runner.py: run() drives the daemon, _wait_phase() polls with a cap, zap_category() performs the keyword mapping. Imported ZAP JSON reports go through scanner/importer.py.

08 · Normalization

From raw output to a finding

Two layers turn tool output into candidates, and they are deliberately different. Rules handle facts. AI handles interpretation. Neither is allowed to confirm anything.

Layer one: the deterministic normalizer

The normalizer reads the raw output of completed prober and ZAP jobs. It creates a finding only when the statement is unambiguous: a header is missing, a cookie lacks a flag, a certificate is expired, ZAP raised an alert. Each finding starts as ai_candidate, gets the tool's suggested severity, and carries a slice of the raw output as evidence.

Duplicates are suppressed by exact title within one assessment. That makes retries and repeated normalization idempotent. It also has a known consequence: two tools can describe the same weakness with different titles, and both will appear. The assessor sees the overlap and dismisses one. Exact-title deduplication is simple and predictable; fuzzy matching would silently hide findings.

Layer two: the AI interpreter

After normalization, the interpreter sends the raw outputs to a language model with a strict job: find what the rules cannot. Non-obvious combinations, risky configuration patterns, and intelligence worth investigating. It is explicitly told not to restate the deterministic findings unless it adds a new interpretation.

Table 11. Guard rails on the AI layer
ConstraintEffect
JSON-schema-constrained outputEach candidate must have a title, description, category, severity, confidence, and optional remediation.
Maximum 10 findingsKeeps the output reviewable and prevents a wall of speculation.
Minimum confidence 0.3Low-confidence guesses are dropped before they reach the assessor.
Severity must be a known tierAnything else falls back to low, never to a made-up level.
Exact-title deduplicationThe AI cannot collide with a rule-based finding of the same name.
Redaction before every callSecret patterns and target-specific terms are stripped before the prompt leaves the machine.
Failure is non-fatalA missing provider or bad output degrades to the rule-based result plus a note.

The AI's confidence is stored separately from the severity. A candidate can be high severity and low confidence, which is a very different review task from high severity and high confidence. Rule-based candidates are stored with confidence 1.0, because the rule itself is certain; that does not make the conclusion certain.

Why two layers

Deterministic checks are cheap, fast, and reproducible. They are also blind to context. A model is good at context and bad at guarantees. Running rules first means the AI never has to waste effort on "is this header present?", and the assessment still has value when no model is configured. The two layers are complementary, not competing.

In the code

backend/app/scanner/normalize.py: normalize_job() and create_candidate(). backend/app/ai/interpret.py: interpret_assessment(), the schema, and the repair-retry loop.

09 · Risk

How severity works

Severity is the most misunderstood number in security. It is not a property of a tool output. It is a judgement about a specific weakness, on a specific system, with a specific exposure. Aletheia separates the suggestion from the decision, and documents the reasoning in between.

9.1 The five tiers

Table 12. Severity tiers in practice
TierIn one sentenceA realistic exampleWhat an assessor does
critical Someone can take control or reach data at scale, usually without special conditions. An unauthenticated endpoint returns every user's records; live production credentials are public. Treat it as an incident. Fix or take the service offline before the report is signed.
high A realistic attack causes serious harm, but needs a condition, some skill, or a second mistake. Stored cross-site scripting on a page an administrator visits; SQL injection behind a login. Fix in the current cycle. Block release if this is production.
medium It weakens a defence or leaks useful information; harm needs an extra step. HSTS missing; self-signed certificate; a debug log left public. Schedule the fix. Document any compensating control if it is delayed.
low Hygiene: little direct harm, but it makes other attacks easier or signals neglect. X-Frame-Options missing; a cookie without Secure on a plain-HTTP demo. Batch with routine maintenance.
info Not a weakness by itself; context that helps the assessor. Server banner; X-Powered-By; an open port that is expected. Record it. No fix required unless it changes the picture.
Severity is contextual

The same missing header can be medium on a static brochure site and high on an application that renders user content. The tier is not a property of the header; it is a property of the header here. That is why the assessor, not the scanner, owns the final value.

9.2 Where the first suggestion comes from

  • The prober uses a fixed table. Missing CSP is high, HSTS medium, the two low-impact headers low, Permissions-Policy info, expired certificate high, self-signed medium. These are defensible defaults, not context-aware judgements.
  • ZAP supplies its own risk field. It is a four-level scale with no critical tier.
  • The AI interpreter proposes a severity from the raw outputs. It is constrained to the five valid tiers, and its confidence is stored separately.

All three are suggestions attached to a candidate. None of them changes a finding's status to verified.

9.3 The logic: OWASP likelihood × impact

Aletheia uses the qualitative form of the OWASP Risk Rating Methodology. Instead of inventing a number, the assessor answers two questions on a three-point scale.

Table 13. The two axes
AxisThe questionWhat pushes it up
Likelihood How likely is it that someone would find and exploit this, here? Low skill needed, a motivated attacker, easy discovery, easy exploitation, little chance of being noticed.
Impact If they did, how much damage would it cause? Confidentiality loss, data tampering, outage, lost accountability, financial, reputational, or legal damage.

Each axis is rated low, medium, or high. The pair maps to a tier through a fixed 3×3 matrix.

Table 14. The rating matrix
Likelihood \ ImpactLow impactMedium impactHigh impact
Low likelihoodinfolowmedium
Medium likelihoodlowmediumhigh
High likelihoodmediumhighcritical

The intuition is easiest with physical security. A broken window on a shed behind a fence is easy to see (high likelihood) but low impact: it is a shed. A vault door left unlocked inside a bank is hard to reach (low likelihood) but catastrophic if reached (high impact). A missing lock on the bank's front door is both easy and catastrophic, and that is the only cell that reaches critical.

Worked ratings

Table 15. How the matrix produces the tool defaults
FindingLikelihoodImpactResultReasoning
Missing Content-Security-Policy HighMedium high Any scanner sees it instantly, and XSS payloads are cheap. But the missing header removes a safety net; it does not by itself leak data.
Server banner discloses a version LowLow info Easy to read, but it grants nothing. It only shortens an attacker's research step.
Outdated library with a known exploit MediumHigh high Exploits are public, but the attacker still needs a reachable code path and a working payload.
Public .env with live database credentials HighHigh critical The file is directly fetchable and the credentials grant the data. The prober seeds this as high; the assessor raises it after reading the evidence.
The default is a starting bid

The prober's table is an approximation of this matrix, written once so the common cases are consistent. It cannot know that the exposed .env contains live production keys, or that the missing CSP sits on a page that renders user HTML. That gap is the assessor's job, and it is why the platform records both the tool's suggestion and the human's final value.

9.4 The 0–10 score

Tiers are good for humans and bad for sorting. Reports and risk registers need a number. Aletheia maps each tier to a band on a 0–10 scale, and shows one representative value per band when the assessor has not set an explicit score.

Table 16. Score bands and representative values
Score rangeTierRepresentative value
0.0 – 0.9info0.0
1.0 – 3.9low2.5
4.0 – 6.9medium5.5
7.0 – 8.9high8.0
9.0 – 10.0critical9.5

The representative value is the middle of the band, not its boundary. A high finding shows 8.0 rather than 7.0 or 8.9, which avoids implying a precision the judgement does not have. If the assessor sets an explicit score, that value wins. Out-of-range values are clamped to 0–10, never wrapped around.

The two mappings are inverses of each other: a tier gives a representative score, and a score gives back its tier. That symmetry is unit-tested, and the matrix in the methodology document is parsed by a test and compared cell by cell with the code, so documentation and implementation cannot drift apart silently.

9.5 Who has the final say

Only a signed-in assessor, or an admin acting in that role, can change the authoritative severity. The API records that person's identity and the timestamp, and the finding's status moves to verified, needs_evidence, or false_positive. A viewer can read everything and change nothing.

This is the platform's central ethical constraint, not a UI nicety. The course brief requires a human in charge of what counts as a confirmed vulnerability, and the data model enforces it: there is no code path that sets a finding to verified without an action from a permitted human role.

9.6 Where severity appears

  • Finding badges use one semantic colour per tier: red, orange, amber, blue, grey. The colours are state, not decoration, and they work in both themes.
  • The dashboard shows the severity mix and, separately, verification progress. A wall of red is a work queue, not a verdict.
  • The report groups findings by tier, shows each score, and derives the overall posture from the highest tier present.

9.7 A severity decision, traced

Take a finding titled "Missing security header: content-security-policy" on a lab application.

  1. The prober sees no CSP header. It creates a candidate with severity high, confidence 1.0, and the response headers as evidence.
  2. The AI interpreter may add context, for example that the application reflects search terms into the page. It does not change the rule-based finding.
  3. The assessor opens the evidence. Likelihood is high: the header is absent on every page and the scanner found it in one request. Impact is medium: the header is a defence, not the vulnerability itself.
  4. High × medium maps to high in the matrix. The assessor accepts the suggested tier and leaves the score blank, so the report shows the representative 8.0.
  5. The status becomes verified, with the assessor's ID and timestamp. The report now counts it as confirmed.

If the same header were missing on a page that never renders user input, the assessor could lower the impact to low and the tier to medium, with a note explaining why. That is not inconsistency; it is the method working as intended.

In the code

backend/app/risk.py: RISK_MATRIX, SCORE_BANDS, REPRESENTATIVE_SCORES, risk_rating(), severity_for_score(). The prose version is docs/risk-methodology.md, and backend/tests/test_risk_model.py keeps the two in sync.

10 · Guard rails

The safety rails

A scanning platform is a dual-use tool. The difference between an assessment and an attack is authorization, scope, and restraint. Aletheia enforces all three in code, not in a checkbox.

Table 17. Enforcement points
GateWhat it stopsWhere it is enforced
Host guard Contacting private, loopback, link-local, reserved, or cloud metadata addresses without an authorization record. Before every runner opens a socket, and on every redirect hop for HTTP requests.
Intensity gate Running intrusive tools against a target that only allows passive assessment. API creation (HTTP 409) and the orchestrator's runtime re-check.
Scope filter Probing paths the target owner listed as out of scope. The prober's path list is filtered before any request is sent.
Redaction layer Sending credentials or target-identifying terms to a language model. Every LLM call, before the request leaves the process.
Human verification Treating a tool or AI guess as a confirmed vulnerability. The finding state machine and the report's confirmed counts.

The host guard, in detail

Checking the URL string is not enough. A hostname is not an address: localhost, 127.0.0.1, and a DNS name pointing at 10.0.0.5 can be the same machine, and a public host can redirect to any of them. The guard therefore resolves the name first, then classifies every address it gets.

Table 18. Host policy
Address classAllowed?Condition
PublicYesNormal registered target.
Private, loopback, link-local, reservedOnly with authorizationThe target must have a non-empty authorization reference and list the host in its in-scope assets.
Cloud metadata (169.254.169.254 and peers)NeverBlocked even with an authorization record. Instance credentials are never an assessment target.

The guard is deliberately one module used by DNS, Nmap, the prober, and ZAP, so the policy cannot drift between tools. The prober adds a request hook that repeats the check on every redirect, which closes the "public host bounces you to an internal address" path.

Secrets and the AI boundary

LLM provider keys are encrypted at rest and are never returned by any API response or written to a log. Before any content is sent to a model, a redaction layer strips common secret patterns (keys, tokens, passwords) and a per-target deny list of names, hosts, and scope identifiers. The model sees the shape of the evidence, not the customer's identity.

The trade-off that is documented, not hidden

Scan execution is in-process, by design, because Celery and Redis were explicitly cut from scope. Jobs are persisted, so the UI survives a refresh, but a server restart kills a running scan. The assessment row stays running in the database and can be relaunched. This is a known limitation, not an accident, and it is recorded in the plan and the member log.

In the code

backend/app/scanner/hostguard.py: check_host(), classify_address(), request_guard(). The intensity gate lives in orchestrator.py and api/assessments.py. Redaction lives in backend/app/ai/redaction.py.

11 · Worked example

A full run, end to end

This is what the pipeline looks like on a local OWASP Juice Shop instance registered as http://localhost:3000, with an authorization reference and full intensity. The counts are illustrative; the behaviour is what the code does.

Table 19. One assessment, job by job
StepWhat happensWhat it becomes
DNS localhost resolves to 127.0.0.1. No MX, NS, or TXT records. The ten subdomain guesses do not resolve. Context only. No findings.
Nmap The URL has an explicit port, so Nmap scans only port 3000. It finds TCP 3000 open, service http, with a Node.js/Express fingerprint. Context and evidence. No finding by itself.
Prober One GET returns 200. Missing CSP, HSTS, X-Frame-Options, and Referrer-Policy. A Server header is present. Cookies lack flags. TLS is skipped because the target is HTTP. Six or seven deterministic candidates, each with headers as evidence.
ZAP The spider maps the single-page routes. The active scan runs because intensity is full. Alerts include CSP not set, anti-clickjacking header missing, and X-Content-Type-Options missing. Alerts become candidates, mapped to categories by keyword.
Normalizer Creates candidates from the prober and ZAP outputs. Exact-title duplicates are skipped. A readable HTTP transcript is attached to prober findings. One candidate list, all ai_candidate.
AI Reads up to 6,000 characters per job, after redaction. Adds a small number of contextual candidates, for example that the framework fingerprint plus a missing CSP raises the value of any reflected input. Up to 10 extra candidates, confidence-scored.
Assessor Verifies the real ones, dismisses the login-redirect false positive, and asks for evidence on one ambiguous alert. Sets severity and optional scores. Verified findings with an audit trail.
Report Groups by severity, shows scores and evidence, includes the methodology note. PDF for the assessment record.

Two things are worth noticing. First, the tools overlap: the prober and ZAP both notice the missing CSP, with different titles, so the assessor sees two candidates for one weakness and dismisses one. Second, the most valuable finding may be a combination: an outdated framework fingerprint plus a missing CSP plus a reflected parameter is more interesting than any one of them alone. That is the kind of judgement the AI layer is for, and the kind of conclusion it is not allowed to confirm.

12 · Boundaries

Limits and honest notes

A document that only describes strengths is marketing. These are the real boundaries of the current implementation, written down so they can be defended rather than discovered.

Coverage

  • Nmap does not scan all 65,535 ports. It scans the top 1,000 or 5,000, and only the URL's explicit port when one is present.
  • No OS detection and no NSE scripts. Both were cut deliberately for privilege, safety, and scope reasons.
  • The prober checks the base URL and a fixed path list, not every page. It does not log in, crawl, or exercise multi-step flows.
  • TLS facts are collected only for HTTPS on port 443. An HTTPS service on a non-standard port gets no certificate findings.
  • ZAP sees what its spider can reach. Authenticated areas and complex JavaScript flows may be under-mapped.

Accuracy

  • A missing header is a missing defence, not a proven exploit. The finding is real; the danger depends on context.
  • Redirects are followed. A protected admin path that redirects to a login page can still be counted as reachable.
  • Deduplication is by exact title. Two tools can report the same weakness under different names.
  • AI output can be wrong. Confidence is an estimate, not a guarantee. That is the reason every AI finding starts as a candidate.
  • Severity defaults are approximations. They are consistent, not context-aware. The assessor's value is the one that counts.

Environment

  • The pipeline is single-process. A server restart kills a running scan; the database row stays running and the run can be relaunched.
  • Tool availability is assumed but not required. A missing Nmap or ZAP fails only that job, with an actionable message.
  • This is an assessment aid, not a replacement for a manual penetration test. It finds what its tools and rules can see, and it says so.
13 · Reference

Glossary

The terms a non-specialist is most likely to meet while reading a report.

Port
A numbered channel on a machine. One address can host many services, each on its own port.
Protocol
An agreed language for a conversation. HTTP is the web's protocol; TCP is the transport most web traffic uses.
HTTP header
A labelled line of metadata attached to a request or response, such as Content-Type or Server.
Cookie
A small note the server asks the browser to store and send back, commonly used to identify a session.
TLS certificate
A signed document that binds a hostname to a cryptographic key, allowing browsers to trust an encrypted connection.
DNS
The system that translates human-readable names into IP addresses.
A record
The DNS entry that maps a name to an IPv4 address. AAAA does the same for IPv6.
Subdomain
A name in front of a domain, such as admin.example.com. Forgotten subdomains are a common exposure.
Payload
The part of an attack request designed to trigger a weakness, for example a script tag or an injection string.
Cross-site scripting (XSS)
Injecting script into a page so it runs in another user's browser, often to steal a session.
SQL injection
Inserting database commands through an input field so the application executes them.
Clickjacking
Loading a real page invisibly inside another and tricking a user into clicking something they did not intend.
MIME sniffing
A browser guessing a file's type from its content instead of trusting the declared type. It can turn an innocent upload into executable script.
CWE
Common Weakness Enumeration: a public catalogue of weakness types, used to compare findings across tools.
OWASP
The Open Worldwide Application Security Project, publisher of the Risk Rating Methodology and the Top 10.
Candidate
A finding produced by a tool or AI that has not yet been verified by an assessor. It is visible, but not confirmed.
False positive
A finding that looked real to a tool but is not a real weakness in context. It is dismissed, not deleted.
Evidence
The proof attached to a finding: a tool output, an HTTP transcript, a screenshot, or an uploaded file.
SSE
Server-Sent Events: a one-way stream from the server that lets the browser show live job progress without polling.
