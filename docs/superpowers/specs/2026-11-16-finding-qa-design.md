## 1. Intent and Why

### Context
In security assessments, findings generated by scanners (such as ZAP, Nmap, or HTTP probers) often contain complex technical evidence (raw HTTP request/response headers, status codes, socket banners, XML/JSON alert payloads). Security assessors evaluating candidate vulnerabilities frequently need to cross-examine this evidence to answer critical assessment questions:
- Is this finding exploitable without existing credentials?
- Does the captured HTTP transcript actually demonstrate an unauthenticated state or missing security header?
- How should the web server (Nginx/Apache) be configured to remediate this specific defect?
- Could environmental quirks (such as reverse proxy rewrites) make this a false positive?

### The "Why"
The course project brief explicitly requires AI-assisted security analysis and includes:
- **Core Feature 04**: *"Explaining potential vulnerabilities"* and *"Suggesting vulnerability remediation"*.
- **Rubric Section C (20 pts)**: Testing the student's *"Understanding of AI integration and limitations"* and ability to handle *"Technical questions and individual demonstration"*.
- **Explicit Constraint (Brief Page 4)**: *"A simple chatbot that only answers general cybersecurity questions will not satisfy this requirement."*

### Intent
Finding Q&A implements a specialized, evidence-grounded analyst assistant embedded directly within the Finding Detail view. It receives the finding's technical context, its full attached evidence items, and the assessor's query, and produces a structured, evidence-cited answer with chain-of-thought reasoning (when supported by reasoning models like DeepSeek-R1). It is strictly not a general chatbot: it refuses to speculate on details not present in the evidence.

---

## 2. Goals, Non-Goals, and Anti-Goals

### Goals
1. **Strict Evidence Grounding**: The system prompt and context assembler strictly bind the LLM to the finding's verified data and attached evidence items (`http_transcript`, port banners, ZAP alerts).
2. **Interactive Analyst UI (shadcn AI Elements pattern)**: Provide a modern, responsive chat interface inside the Finding Detail view featuring quick-prompt chips, user/assistant message bubbles, collapsible reasoning steps, and evidence citation tags.
3. **Audit Trail**: Every question-and-answer exchange is automatically persisted to the `ai_outputs` table with `task=LLMTask.qa`, finding reference, model name, and timestamp.
4. **Credential Protection**: All queries and context pass through the platform's multi-layered `redact_all(...)` scrubber before leaving the host.
5. **Fail-Soft Architecture**: If no AI provider is configured in Settings or if the provider fails, the platform degrades gracefully without breaking the core findings workflow.

### Non-Goals
1. **Unbounded General Chat**: It will not serve as a generic conversational assistant. Questions outside the context of the specific finding will be politely redirected back to the finding's scope.
2. **Automated Verification State Changes**: The assistant will never automatically change a finding's status (`ai_candidate`, `verified`, `false_positive`). Verification decisions remain strictly in human assessor hands.
3. **Cross-Assessment Aggregations**: This feature is per-finding; it does not aggregate or correlate across unrelated assessments.

### Anti-Goals
1. **Hallucinated Exploits**: Under no circumstances should the model assert that a vulnerability is exploitable unless the attached evidence demonstrates the prerequisite conditions.
2. **Credential or Secret Leakage**: Raw session tokens, API keys, and target authorization credentials must never survive into prompts or response logs.

---

## 3. Constraints

1. **Security & Redaction**: Adhere strictly to the project rule in `PLAN.md` and `AGENTS.md`: all inputs must be sanitized using `app.ai.redaction.redact_all` with target deny-list terms before transmission.
2. **Human in Charge**: Fulfill the project brief mandate: AI is an advisor; only a human assessor can mark findings as verified.
3. **Stack & Styling**:
   - Backend: Python 3.13, FastAPI, SQLAlchemy 2.0, Pydantic v2.
   - Frontend: React 19, TypeScript, Tailwind CSS v4, shadcn/ui primitives.
   - UI Rules: Support both dark and light modes cleanly. No em-dashes in user-facing copy.
4. **Testing**: Must include deterministic mock-transport tests verifying grounding, reasoning extraction, error handling, and secret redaction.

---

## 4. Approaches Considered & Trade-Offs

### Approach 1: Threaded Grounded Assistant with shadcn AI Elements (Selected)
- **Description**: A request/response API endpoint (`POST /api/findings/{id}/qa`) supporting conversational context within the current viewing session. The UI utilizes shadcn AI Elements design patterns (quick question chips, message bubbles, collapsible reasoning process, and evidence citations).
- **Why Chosen**: Maximizes demonstration value for examiners; maintains deterministic error handling and audit logging; strictly enforces redaction on full payloads; perfectly compatible with `httpx.MockTransport` test seams.

### Approach 2: Token-by-Token Streaming Assistant (Rejected)
- **Description**: SSE-based streaming assistant.
- **Why Rejected**: Redaction of streaming chunks risks token-boundary credential leaks; complicates persistence of complete audit logs in `ai_outputs`; introduces unnecessary complexity for answers that typically take 1 to 2 seconds to complete.

### Approach 3: Static Pre-Canned Inquiries (Rejected)
- **Description**: Fixed button options with no free-text input.
- **Why Rejected**: Stiff and does not provide an interactive demonstration of AI reasoning to examiners.

## 5. Technical Specifications

### A. Backend AI Layer: `backend/app/ai/qa.py`
A dedicated module consuming the existing `ai_client.chat` helper:
```python
def answer_finding_question(
    db: Session,
    finding: Finding,
    question: str,
    history: list[dict[str, str]] | None = None,
    *,
    deny_list: list[str] | None = None,
    transport=None,
) -> dict:
    """Answers an analyst question grounded strictly in the finding's technical evidence.
    Returns: {
        "answer": str,
        "reasoning": str | None,
        "model": str,
        "grounded_evidence_ids": list[int],
    }
    """
```
- **Context Assembly**:
  - Finding properties: Title, Category, Severity, CVSS Score, Description, Remediation draft.
  - Attached Evidence: Iterates over `finding.evidence`.
    - Auto-captured evidence (`tool`, `transcript`, etc.): reads `content` (up to 4,000 chars).
    - Uploaded evidence (`kind="upload"`): if file exists on disk with a text extension (`.txt`, `.log`, `.json`, `.http`, `.xml`), reads up to 4,000 chars; if binary/image, passes filename and label with a note that raw binary contents are omitted.
  - Target Context: Base URL, Scope.
- **Output Protocol & Citation Extraction (Reasoning Model Safe)**:
  - Models (especially reasoning tiers like DeepSeek-R1 / `deepseek-reasoner`) often reject strict JSON schema mode. Therefore, the prompt instructs the model to return clear Markdown and tag cited evidence using `[Evidence #<id>]`.
  - The backend extracts `grounded_evidence_ids` using regex `re.findall(r'\[Evidence #(\d+)\]', answer)` validated against the finding's actual evidence IDs.
  - The model's reasoning trace (if provided in `reasoning_content`) is captured separately and returned in the `reasoning` field.
- **System Prompt**:
  Instructs the LLM to act as a senior web security specialist reviewing an authorized finding. Mandates:
  1. Base assertions strictly on the provided technical evidence items (citing evidence IDs where applicable).
  2. If the evidence does not support answering the question, state clearly what data is missing.
  3. Never recommend destructive actions or off-target activity.
- **Redaction**:
  - `redact_all` is executed on both the user question and the assembled evidence context with target deny-list terms.
- **Audit Logging**:
  - Creates an `AIOutput` record:
    - `task = LLMTask.qa`
    - `assessment_id = finding.assessment_id`
    - `model = result.model`
    - `content = json.dumps({"question": question, "answer": answer, "reasoning": reasoning})`

### B. Schemas: `backend/app/schemas/findings.py`
```python
class FindingQAMessage(BaseModel):
    role: Literal["user", "assistant"]
    content: str = Field(..., max_length=4000)

class FindingQARequest(BaseModel):
    question: str = Field(..., min_length=1, max_length=2000)
    history: list[FindingQAMessage] = Field(default_factory=list, max_length=6)

class FindingQAResponse(BaseModel):
    answer: str
    reasoning: str | None = None
    model: str
    grounded_evidence_ids: list[int] = Field(default_factory=list)
    created_at: datetime
```

### C. API Endpoint: `backend/app/api/findings.py`
```python
@router.post("/{finding_id}/qa", response_model=FindingQAResponse)
def ask_finding_qa(
    finding_id: int,
    body: FindingQARequest,
    db: Session = Depends(get_db),
    current_user: User = Depends(require_role(Role.assessor, Role.admin)),
):
    ...
```
- Validates finding existence (404 if missing).
- Role restriction: Restricted to `Role.assessor` and `Role.admin` to protect LLM quota and audit trail integrity. (Viewers receive HTTP 403; frontend displays disabled input with explanatory tooltip).
- Checks whether an AI provider and model are configured for `LLMTask.qa`. If missing, raises HTTP 400 with a clear message: `"No AI provider or model is configured for Finding Q&A. Configure one in Settings."`.
- Calls `answer_finding_question`.

### D. Frontend Interface: `frontend/src/pages/finding-detail-page.tsx`
Embedded directly in the Finding Detail page (and also accessible in the modal view):
1. **Chat Lifecycle**: Maintained in local React component state for the current viewing session. Navigating away resets active messages, while every interaction is permanently recorded in `ai_outputs`. A "Clear chat" button allows clearing the local session messages.
2. **Card Header**: "Ask the Analyst (AI Assistant)" with badge indicating the configured model and task tier.
3. **Quick Prompt Chips**:
   - *"Is this exploitable without auth?"*
   - *"What specific evidence proves this?"*
   - *"Provide web server config remediation"*
   - *"What false-positive conditions could apply?"*
4. **Chat Message Stream**:
   - Analyst user message bubble (brand blue accent).
   - Assistant message card with Markdown formatting.
   - Expandable `<Collapsible>` component for `Reasoning / Thinking Process` when `reasoning` is returned by models like DeepSeek-R1.
   - Cited evidence tags (e.g., `[Evidence #12: HTTP Transcript]`) linking to the evidence section above.
5. **Prompt Input**:
   - Shadcn text area with Enter-to-send (Shift+Enter for newline).
   - Send button with loading spinner when pending.
   - Disabled with tooltip if logged in as `viewer`.
   - Clear history button.

## 6. Verification and Testing Plan

1. **Backend Tests (`backend/tests/test_finding_qa.py`)**:
   - `test_finding_qa_success`: Mock transport verifies finding context and evidence are formatted in prompt; verifies structured response and `ai_outputs` audit record.
   - `test_finding_qa_captures_reasoning_content`: Verifies `reasoning_content` is parsed and returned separately.
   - `test_finding_qa_redaction`: Table-driven test proving target passwords, authorization tokens, and deny-list terms in the question or evidence are scrubbed before reaching the transport.
   - `test_finding_qa_no_provider_configured`: Verifies HTTP 400 with actionable error when `LLMTask.qa` has no assigned model.
   - `test_finding_qa_history_capping`: Verifies history is limited to prevent runaway prompt bloat.

2. **Frontend Quality Verification**:
   - `npm run build`: Zero TypeScript/Vite compilation errors.
   - `npm run lint`: Zero oxlint errors.
   - Visual checks: Dark and light theme contrast, smooth keyboard navigation, responsive layout.
